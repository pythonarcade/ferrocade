# Research: Phase 4 — Keyboard Control

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-10-12

## R1. One key table for desktop and web

- **Decision**: the core defines a `Key` enum (`crates/ferrocade/src/input.rs`) with stable integer
  codes. Each key carries its **W3C UI Events `code` name** (`"KeyW"`, `"ArrowLeft"`, `"ShiftLeft"`,
  `"MetaLeft"`, `"Numpad7"`, ...) and its Python constant name (`W`, `LEFT`, `LSHIFT`, ...).
  - **Desktop:** the platform layer maps winit's `PhysicalKey::Code(KeyCode)` to `Key`. winit's
    `KeyCode` variants are named after the same W3C spec (verified in winit 0.30.13
    `src/keyboard.rs`; the one rename is `Meta*` → `Super*`).
  - **Web:** the browser's `KeyboardEvent.code` is exactly the W3C name, so the web crate maps it
    with the core's `Key::from_code_name`.
- **Rationale**: one table, physical keys on both platforms (FR-003), and no per-platform drift.
  Tests check that every `Key` has a unique code name and that the winit mapping covers every `Key`.
- **Alternatives**: `KeyboardEvent.key` / winit's logical key (layout-dependent, so it breaks WASD on
  AZERTY); pyglet/Arcade integer values (they're tied to pyglet's virtual keys and gain nothing).

## R2. Python constants: `fc.key` as a generated, shared pure-Python module

- **Decision**: `python/ferrocade/key.py` holds plain `int` constants (`LEFT = 37`-style values
  from the core table) plus `MOD_SHIFT`, `MOD_CTRL`, `MOD_ALT`, `MOD_SYSTEM`, and a
  `name(key) -> str` helper for debugging. It's generated by `tools/gen_keys.py` from the built
  extension's `_ferrocade._key_table()`, and checked in. The web loader copies the same file into
  Pyodide (as it already does for `color.py`), so desktop and web share one source.
- **Rationale**: plain ints are the cheapest values to pass to a callback (constitution II) and match
  Arcade's style. A checked-in module works unchanged in the browser. A test fails if `key.py` and
  the Rust table drift apart.
- **Alternatives**: an `IntEnum` (slower, and nicer reprs aren't needed now that `key.name()`
  exists); constants defined only in Rust (the web shim couldn't share them).

## R3. Event flow and timing

- **Decision**: a core `Keyboard` struct (inside the shared `WindowState`) holds a queue of raw
  events and the set of held keys.
  - The platform pushes raw events (`key`, `pressed`, `repeat`) as they arrive.
  - At the start of each frame, **before** the fixed-timestep updates, the loop calls
    `Keyboard::drain()`. That applies each event in order: it drops OS repeats and duplicate presses
    (a press for a key already held), drops releases for keys not held, updates the held set, and
    returns the accepted `KeyEvent { key, pressed, modifiers }` list. The loop then calls
    `on_key_press` / `on_key_release` for each one, without holding the state lock.
  - `is_key_pressed` reads the held set.
- **Rationale**: callbacks and polling always agree. Events are never delivered in the middle of
  `on_update` or `on_draw` (FR-008), and `on_update` sees every event that arrived before it
  (FR-006). Releasing the lock before calling Python avoids deadlocks when a callback calls
  `is_key_pressed`.
- **Alternatives**: updating the held set when an event arrives (polling could then disagree with
  callbacks that haven't been delivered yet); calling Python straight from winit's event handler
  (that would interleave input with the update/draw sequence).

## R4. Auto-repeat, modifiers, focus loss

- **Auto-repeat**: winit's `KeyEvent::repeat` and the browser's `KeyboardEvent.repeat` mark repeats.
  `drain()` drops them, and also drops any press for a key that's already held (a safety net for
  platforms that don't flag repeats).
- **Modifiers**: computed from the held set **after** applying the event: `MOD_SHIFT` if `LSHIFT` or
  `RSHIFT` is held, and so on. Pressing Shift therefore reports `MOD_SHIFT`, and releasing it doesn't.
  This works the same way on every platform, with no OS modifier queries. A modifier that was
  pressed before the window got focus isn't known (documented).
- **Focus loss**: winit's `WindowEvent::Focused(false)`, and the browser's `blur` (on the canvas and
  the window) plus `visibilitychange` (hidden), call `Keyboard::release_all()`. That queues a
  release for every held key, so the game receives `on_key_release` for each (FR-007).

## R5. Browser input wiring and page scrolling

- **Decision**: the web crate attaches `keydown`, `keyup`, and `blur` listeners to the canvas with
  `web-sys` closures, sharing an `Rc<RefCell<Keyboard>>` with the `Engine`. The canvas gets
  `tabindex="0"`, focus on start, and focus on click. `preventDefault()` is called for every
  recognized key **unless** Ctrl, Alt, or Meta is held, or the key is Tab or F1–F12.
- **Rationale**: arrow keys, Space, PageUp/PageDown, Home/End and `/` (quick-find) no longer act on
  the page (FR-011), while browser shortcuts (Ctrl+R, F5, F12, Ctrl+W) and Tab focus navigation
  keep working.
- **Python side**: the shim calls `_engine.take_key_events()` once per frame. It returns a flat
  `Int32Array` of `[key, pressed, modifiers, ...]`. The shim keeps its own held set from those
  events, so `is_key_pressed` needs no JS call. That's one boundary crossing per frame.
- **Alternatives**: listening in `loader.js` (logic would split across JS and Rust); listening on
  `document` (keys would be captured even while the user types in other page elements).

## R6. Testing without a real keyboard

- **Rust**: unit tests for `Keyboard` (repeat filtering, duplicate presses, modifiers, `release_all`,
  ordering) and for the mapping tables.
- **Desktop Python**: a private `Window._inject_key(key, pressed, repeat=False)` pushes a raw event
  into the same queue the platform uses. Tests inject from inside `on_update` and check the
  callbacks and `is_key_pressed` on following frames, so the real delivery path is exercised end to
  end. Focus loss is tested through a private `Window._inject_focus_lost()`.
- **Browser**: `tools/web-check/check.mjs --keys` focuses the canvas, holds `ArrowRight` with
  puppeteer (real DOM `KeyboardEvent`s with `code`), and checks that the ship's x increased while y
  stayed put and `window.scrollY` stayed 0.
- **Manual**: the owner steers the example on desktop (quickstart V3–V5).

## R7. Example design

- `examples/04_keyboard_ship.py`: polling (`is_key_pressed`) in `on_update` builds a direction from
  the arrow keys and WASD, normalizes it, and sets `ship.velocity = direction × 300 px/s`. The engine
  moves the ship (`SpriteList.update`), then the example clamps it inside the window.
  `on_key_press(fc.key.SPACE)` re-centers the ship, so both input styles are shown.
- There's no "quit on Escape", because `Window.close()` doesn't exist yet (it's a backlog
  candidate, not added here; principle IV).
